原文説明（英語）

<p>Three verifier agents. One milestone. Real ETH at stake.</p> <p>The first time I ran the consensus loop without tracing, a silent timeout in the peer broadcast caused two nodes to vote while the third sat idle. The quorum passed anyway (2-of-3), but I had no idea the third node was broken until I checked the logs manually — 40 minutes later.</p> <p>That's when I stopped treating observability as a nice-to-have and started treating it as the product.</p> <p>What I Built</p> <p>Weft is an autonomous milestone verifier: builders stake ETH against project deliverables, and when a deadline passes, three independent AI agents gather evidence — contract deployment, on-chain usage, GitHub commits — corroborate over encrypted channels, and execute a verdict on-chain. Capital releases or refunds automatically.</p> <p>The stack:</p> <p>Python verifier daemon<br /> 0G Chain smart contracts<br /> Zama FHE for sealed ballot privacy<br /> AXL for peer-to-peer messaging<br /> SigNoz for the entire observability layer<br /> The Instrumentation That Actually Mattered</p> <p>I instrumented the daemon with OpenTelemetry's Python SDK — standard stuff at first: one root span per verification cycle, child spans for each evidence-gathering step. But the useful instrumentation came from the places I didn't initially think to trace.</p> <ol> <li>The peer broadcast</li> </ol> <p>Each verifier broadcasts its signed verdict envelope to the other two nodes via HTTP POST. I wrapped the broadcast call in a span with attributes for peer.address, envelope.evidence_root, and response.status.</p> <p>python<br /> with tracer.start_as_current_span(<br /> "axl.broadcast_verdict",<br /> attributes={<br /> "peer.address": peer_url,<br /> "milestone.hash": milestone_hash,<br /> "envelope.evidence_root": evidence_root,<br /> },<br /> ) as span:<br /> resp = requests.post(f"{peer_url}/send", json=envelope, timeout=10)<br /> span.set_attribute("http.status_code", resp.status_code)</p> <p>When the third node was timing out, the span showed a 30s duration with a deadline_exceeded status — something I'd never have found in stdout logs, because the daemon's retry logic silently moved on.</p> <ol> <li>The consensus wait</li> </ol> <p>When AXL_WAIT_FOR_PEERS=1, the daemon polls its inbox for matching peer envelopes before voting. I added a span that tracks how long consensus took to form and how many unique signers contributed. In SigNoz, this shows up as a variable-width bar in the waterfall — you immediately see whether consensus was fast (all nodes healthy) or slow (one node lagging).</p> <ol> <li>The FHE ballot encryption</li> </ol> <p>Zama's FHEVM operations are computationally expensive. A span around submit_encrypted_weighted_verdict revealed it was taking 4–6 seconds per call — 10x longer than the regular submitVerdict. That's fine once you know it. Without the span, the total cycle time just looked "slow," with no obvious bottleneck.</p> <p>What SigNoz Gave Me That Logs Didn't</p> <p>The dashboard I actually lived in had eight panels:</p> <p>Verification cycle duration (p50/p95) — one number that told me if something was degrading<br /> Evidence source availability — three gauges for GitHub API, RPC node, and 0G indexer<br /> Peer consensus formation time — how long from first broadcast to quorum<br /> Transaction success rate — did the on-chain verdict actually land<br /> Per-node vote status — which verifiers voted, which are stuck<br /> FHE encryption latency — the Zama call specifically<br /> Active milestone count — workload across pending deadlines<br /> Error rate by span — which operation is failing most</p> <p>The trace waterfall is where debugging actually happened. A single verification cycle produces 15–25 spans:</p> <p>deadline_scheduler.poll<br /> → indexer_client.get_milestone<br /> → metadata_reader.read<br /> → github_client.collect<br /> → eth_rpc.get_code<br /> → mvp_verifier.count_callers<br /> → kimi_client.generate_narrative<br /> → axl_client.broadcast<br /> → peer_inbox.wait_for_consensus<br /> → keeperhub_client.execute_verdict</p> <p>When something breaks, you click the trace and see exactly where.</p> <p>The thing that surprised me: I used trace-to-logs correlation more than I expected. The daemon emits structured JSON logs with trace IDs, so clicking a suspicious span in SigNoz jumps straight to the exact log lines from that operation. This was invaluable when debugging a case where evidence-gathering passed but the attestation JSON was malformed — the span said "success," but the log showed a missing field that only mattered downstream.</p> <p>What I'd Tell My Past Self</p> <p>Instrument the boundaries, not the internals. I wasted time tracing individual lines of business logic. The useful spans were at system boundaries: HTTP calls to peers, RPC calls to the chain, API calls to GitHub/Kimi/0G. Internal function calls are better served by logs correlated to the parent span.</p> <p>Set span attributes aggressively. milestone.hash, verifier.address, evidence.type, consensus.signer_count — these turn a generic waterfall into a queryable dataset. When I needed to answer "which milestone took longest to verify last week," it was a SigNoz query, not a grep.</p> <p>The alert that saved me: a simple condition — verification cycle &gt; 120s — caught a regression where the 0G indexer RPC was returning stale data. The daemon kept retrying reads for metadata that hadn't propagated yet. I added exponential backoff with a ceiling, but without the alert I'd have burned through rate limits for hours before noticing.</p> <p>Don't trace in production without sampling in mind. Three verifier nodes, each polling every 60 seconds, each producing 15+ spans per cycle — that's roughly 2,700 spans/hour, minimum. Fine for a hackathon. For production, you'd want head-based sampling on the poll cycles and 100% sampling on the verdict-execution path.</p> <p>The Takeaway</p> <p>The point of Weft is that autonomous agents handling money must be observable — not because regulators require it (though they will), but because you need to debug it at 2am when a verdict doesn't land and there's real capital on the line.</p> <p>SigNoz turned "the third node seems broken" from a 40-minute log-spelunking session into a 10-second glance at a trace waterfall.</p> <p>If you're building agents that do anything consequential — transactions, deployments, approvals — instrument the decision path end-to-end before you ship. You'll thank yourself the first time something fails silently.</p> <p>Weft is open source: github.com/thisyearnofear/weft. The SigNoz dashboards are provisioned via OpenTofu in agent/scripts/weft_signoz_provision.sh.</p>

Building a Real-Time AI Voice Agent That Handles 70+ Languages
原文説明
原文説明（英語）

<h3> The problem we started with </h3> <p>Most small businesses still handle phone calls the old way: a human answers, or a menu tree routes the caller to a department. If it's after hours, the call goes to voicemail. If the customer speaks a language the team doesn't cover, the call drops. If the issue needs two departments, the customer repeats themselves twice.</p> <p>We wanted to build an AI agent that could take over those calls — not as a chatbot on a website, but as a real-time voice agent on the phone. And we wanted it to work in 70+ languages without building a separate model for each one.</p> <p>The result is <a href="https://ringbot.ai" rel="noopener noreferrer">RingBot</a>, an Agent-as-a-Service platform. This post is a short technical walkthrough of what we learned building it.</p> <h3> What "real-time voice" actually means </h3> <p>A traditional voice bot works like this:</p> <ol> <li>Speech-to-text (STT) transcribes the audio</li> <li>An LLM generates a text response</li> <li>Text-to-speech (TTS) reads it back</li> </ol> <p>That works, but the latency is noticeable. Every step adds 500ms–1s, and the conversation feels robotic.</p> <p>Real-time voice models like GPT Realtime, Gemini Live, and Grok Voice use an end-to-end audio pipeline. The model listens to raw audio and generates audio back directly, without going through text in the middle. That cuts latency dramatically and makes turn-taking feel natural.</p> <h3> Why we use multiple models </h3> <p>We built RingBot to be model-agnostic. Each real-time model has trade-offs:</p> <ul> <li> <strong>GPT Realtime</strong> is strong at following instructions and handling complex multi-turn tasks.</li> <li> <strong>Gemini Live</strong> is excellent across many languages and has a very natural voice persona.</li> <li> <strong>Grok Voice</strong> gives us a different latency/cost profile and a distinct voice character.</li> </ul> <p>Instead of betting on one model, we route calls to the best model for the job. A caller can even switch models mid-conversation if that improves the experience.</p> <h3> The architecture in four pieces </h3> <p>Our production stack looks like this:</p> <ol> <li> <strong>Telephony gateway</strong> — handles SIP/WebRTC, streams audio to the agent, and manages call state.</li> <li> <strong>Agent orchestrator</strong> — picks the right model, loads the business context, and runs the conversation loop.</li> <li> <strong>Knowledge base</strong> — semantic search over product docs, FAQs, and catalogs so the agent answers with live information, not stale scripts.</li> <li> <strong>Handoff layer</strong> — when a human needs to take over, it transfers the full transcript, intent summary, and customer context to the support agent.</li> </ol> <p>The agent orchestrator is the interesting part. It doesn't just call a model. It also manages intent classification, routing rules, tool calls (e.g., check order status, book an appointment), and escalation thresholds.</p> <h3> The multilingual challenge </h3> <p>The biggest surprise was that multilingual voice is now mostly a solved problem — for the model layer. The harder part is the surrounding system:</p> <ul> <li> <strong>Business context translation:</strong> Your knowledge base is probably in one language. We use retrieval that works across languages, so a Spanish caller can get answers from English docs.</li> <li> <strong>Routing intent across languages:</strong> The agent must recognize that "quiero hablar con ventas" and "I want to speak to sales" mean the same thing.</li> <li> <strong>Voice persona consistency:</strong> We want the same agent personality across languages, not a different voice for each locale.</li> <li> <strong>Latency on low-resource languages:</strong> Some languages are slower on certain models. We monitor real-time latency per language and route accordingly.</li> </ul> <h3> Context is the hard part </h3> <p>Voice conversations move fast. If a caller says, "Actually, I want to change my appointment, not cancel it," the agent has to update its plan immediately. If it then transfers to a human, the receiving agent needs to know:</p> <ul> <li>What the original request was</li> <li>What changed</li> <li>What still needs to be done</li> <li>What tools the AI already called</li> </ul> <p>We solve this by maintaining a structured conversation state that travels with the call. The human agent sees a short summary plus the full transcript, instead of asking the customer to repeat the story.</p> <h3> What we would do differently </h3> <ul> <li> <strong>Start with evaluation tooling.</strong> It's hard to tell if a voice agent is "good" without listening to calls. We built automated evals for latency, turn-taking, and task completion, but we should have done it earlier.</li> <li> <strong>Fail loud and fast.</strong> A confused voice agent that loops forever is worse than one that immediately transfers to a human. We added escalation triggers based on repetition and confidence scores.</li> <li> <strong>Respect platform limits.</strong> Each real-time API has its own quirks around audio formats, rate limits, and session duration. We abstracted these into a provider layer so callers don't need to know which model is running.</li> </ul> <h3> The "no code" layer </h3> <p>Under the hood, this is a fairly technical system. But the end user — a small business owner — shouldn't have to think about telephony, embeddings, or model selection. So we wrapped everything in a config flow: connect your business info, upload your docs, pick a phone number, and deploy.</p> <p>That's the Agent-as-a-Service idea. The user hires an agent, not a toolkit.</p> <h3> Try it or ask questions </h3> <p>If you're building with real-time voice APIs, I'd love to hear what you're running into. And if you want to see a production example, you can check out <a href="https://ringbot.ai" rel="noopener noreferrer">RingBot</a>.</p>

Stop hand-juggling JAVA_HOME: automatic per-project JDK switching with Jolta
原文説明
原文説明（英語）

<p>If you work on more than one Java codebase, you've probably lived this: one service targets JDK 17, another needs 21, and there's a legacy app that will only ever build on 11. Every context switch means resetting JAVA_HOME, or remembering to run a version-switch command, or discovering ten minutes into a weird compiler error that you're on the wrong JDK.</p> <p>There are good tools for this already — SDKMAN!, jenv, asdf, mise. I've used most of them. I built Jolta because I wanted something that leaned all the way into automatic, per-project switching with as close to zero ceremony as possible, and that treated Windows as a real target. This post is the honest tour, including where the existing tools might still suit you better.</p> <p>Full disclosure: Jolta is my project. MIT-licensed, on GitHub at OneAppPlatform/jolta.</p> <p>The idea, borrowed from Node</p> <p>Volta solved this nicely in the Node world: you pin a tool version per project, and the right one is used automatically because your node/npm are actually lightweight shims that resolve the correct version at call time. No cd hook, no "did I remember to switch" ritual.</p> <p>Jolta applies that model to the JDK.</p> <p>bash<br /> cd my-service<br /> jolta pin 21<br /> java -version # → OpenJDK 21, automatically</p> <p>jolta pin 21 writes a .java-version file to the project. From then on, when you invoke java, javac, jar, jshell, and friends, Jolta's shims walk up the directory tree, find the nearest .java-version, and dispatch to the right JDK.
